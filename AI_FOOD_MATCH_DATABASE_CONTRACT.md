# AI Food Match Database Contract

## 1. Table

Actual table name: `public.ai_food_matches`.

The repository migration creates this table with `create table if not exists`. It has now been applied successfully to the shared Supabase project and verified in SQL Editor.

## 2. Schema

| Column | Type | Nullable | Description |
|---|---|---:|---|
| `id` | `uuid` | No | Primary key; defaults to `gen_random_uuid()`. |
| `customer_id` | `uuid` | Yes | Registered customer Auth/Profile ID; foreign key to `public.profiles(id)` with `ON DELETE SET NULL`. |
| `session_id` | `text` | Yes | Server-issued guest AI session identifier. |
| `preferences` | `jsonb` | No | Selected preference keys; defaults to `{}` at database level, although the API sends an array. |
| `top_match_food_id` | `text` | Yes | Identifier of the top matched food as sent by the current AI Food Match client. There is no database foreign key. |
| `match_percentage` | `smallint` | No | Integer match score constrained to `0..100`. |
| `created_at` | `timestamptz` | No | Insert timestamp; defaults to `now()`. |

Table-level constraint: at least one identity is required: `customer_id is not null or session_id is not null`.

## 3. Relationships

### AI Food Match → Customer

`ai_food_matches.customer_id` references `public.profiles.id` (`ON DELETE SET NULL`). The profile row uses the authenticated Supabase user ID.

### AI Food Match → Menu/Food

There is **no database relationship** from `top_match_food_id` to `public.menu_items`; no foreign key exists and the generated TypeScript relationship list is empty. The current API stores the client-provided food identifier as `text`. The Admin Dashboard must therefore treat it as an optional identifier and resolve a name against the current menu source only when the value matches that source.

The live customer menu currently reads `public.menu_items` when available and falls back to `data/budaya-restaurant-menu-2025.json`; this is separate from the activity table contract.

## 4. RLS Policies

The migration enables RLS and defines these policies:

### `ai_food_matches_insert_own`

- Operation: `INSERT`
- Roles: policy is created without a `TO` clause, so it applies to the roles that have insert privilege (`anon` and `authenticated` are granted insert by the migration).
- Registered customer condition: `auth.uid() is not null`, `customer_id = auth.uid()`, and `session_id is null`.
- Guest condition: `auth.uid() is null`, `customer_id is null`, and `session_id is not null`.

### `ai_food_matches_select_own_or_staff`

- Operation: `SELECT`
- Role: `authenticated`.
- Customer condition: `customer_id = auth.uid()`.
- Staff/admin condition: `public.current_user_role() in ('staff', 'admin')`.
- Guest reads: no guest select policy exists; guests cannot read this table directly through the client Data API.

No update or delete policy is defined. No update/delete grants are added by this migration.

## 6. Preferences Format

The API accepts `preferences` as an array of strings, maximum 10 entries, each maximum 32 characters. The current UI sends these rule keys:

```json
["spicy", "noodles", "meat", "rice", "local", "vegetarian", "budget"]
```

The database stores that array in the `jsonb` column. The database does not enforce an enum or array shape; the route validates only string-array length/content limits.

## 7. Food Relationship

There is no enforced `top_match_food_id → menu_items.id` relationship. The current customer flow derives the value from the existing menu item object and sends `item.id`; however, the activity table intentionally stores it as text and does not constrain it to UUID. Developer 2 should:

1. Read activity rows from `ai_food_matches`.
2. Resolve `top_match_food_id` against the same current menu data source used by the customer menu where possible.
3. Display a safe fallback such as `Unavailable menu item` when no match is found.

Do not add a guessed join or alter the schema as part of the Admin Dashboard.

## 8. Recommended Read Query

Reuse the existing typed Supabase server client, `createClient` from `src/lib/supabase/server.ts`, in an authenticated server route/component:

```ts
const supabase = await createClient();
const { data, error } = await supabase
  .from("ai_food_matches")
  .select("id, customer_id, session_id, preferences, top_match_food_id, match_percentage, created_at")
  .order("created_at", { ascending: false });
```

For an Admin Dashboard, first enforce the existing server-side role helper:

```ts
const access = await requireRole(["staff", "admin"]);
if (!access.authorized) { /* return a safe unauthorized response */ }
```

`requireRole` is in `src/lib/auth/roles.ts`. RLS remains the final database enforcement; UI hiding is not sufficient.

## 9. Admin Access

- Authentication: an authenticated Supabase user is required.
- Required role: `staff` or `admin` as returned by `profiles.role` and `current_user_role()`.
- Server utility: `requireRole(["staff", "admin"])` from `src/lib/auth/roles.ts`; use `createClient()` from `src/lib/supabase/server.ts` for the query.
- RLS: the select policy permits a row when `current_user_role()` is `staff` or `admin`.
- No service-role key is required for the normal read path and it must not be exposed to the browser.

## 10. Guest Records

Guest identity is the `nangnyamai_ai_session` HttpOnly cookie. The API creates a cryptographically random UUID with `crypto.randomUUID()` when an unauthenticated request has no existing cookie, then stores it for 30 days at `/`.

For guests, `customer_id` is `null` and `session_id` contains that server-issued value. Because there is no guest select policy, the Admin Dashboard should display the customer label as `Guest` whenever `customer_id` is null; it should not expose the raw session token in the UI.

Registered users use `customer_id = auth.getUser().user.id` and `session_id = null`.
